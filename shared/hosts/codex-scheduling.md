# Codex native scheduling recipe

After roadmap approval, always offer a concrete schedule proposal for a multi-session course unless the learner has declined. Reuse saved cadence/time preferences, suggest a reasonable starting day/time when missing, and ask one question at a time only for required missing details. Confirm the IANA timezone instead of guessing. Summarize days, local time, timezone, missed-run behavior and the wait-for-learner progression rule; get separate schedule consent with `loom_approve_schedule`.

Use only a real Codex native scheduled-task capability available in this session. Call `loom_prepare_native_schedule` with observed capabilities; the MCP server also requires a trusted Codex host adapter to verify them. If the result is `manual-setup` or includes `HOST_ADAPTER_UNAVAILABLE`, say clearly that the schedule is not active, give the returned lesson launch prompt as the manual option, and leave the course manually dispatchable. Do not report a proposed or approved schedule as created.

Before creating a task, confirm that the host supports a fresh chat, the exact IANA timezone and durable access to the same workspace. Use the lesson launch prompt returned by ConceptLoom. After the native host confirms creation, pass the actual schedule ID, timezone, workspace path, execution scope and creation time to `loom_bind_native_schedule`. The binding still requires an installed trusted verifier; caller-supplied claims or a draft receipt are not confirmation. Report the schedule as active only after `loom_bind_native_schedule` succeeds. On a timeout after task creation, reconcile the host state before retrying.

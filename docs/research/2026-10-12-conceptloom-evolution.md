## Запрос и принятые ограничения

ConceptLoom должен поддерживать длительное персональное обучение: диагностику уровня, поиск и подготовку материалов, согласованный курс, уроки в новых чатах по расписанию, вопросы во время урока, интерактивную практику и личный граф знаний.

Пользователь подтвердил: **Codex/ChatGPT и Claude Code Desktop развиваем одновременно, с общим форматом данных**. Расписание курса включаем только после согласия учащегося. Python и LangChain рассматриваем как архитектурный выбор. Приоритет сохраняемой информации: оригиналы источников, пользовательские заметки и подтвержденные результаты обучения.

## Что действительно есть сейчас

| Направление | Реализация в checkout | Недостающая часть |
|---|---|---|

| Диаграммы | `src/diagrams.mjs` оборачивает переданный текст в Mermaid/text fences | Темы, семантический генератор, валидация структуры, HTML и UI resources |
| Большие темы | `route: string[]` в состоянии одного занятия | Объект курса, зависимости уроков, ссылки на материалы, жизненный цикл курса |
| Расписание | Отсутствует в MCP-сервере и установщике | Согласование расписания, интеграции приложений, идентификаторы запусков |
| Источники | Руководство предлагает папки `originals/`, `prepared/`, ручные конвертеры и `prepared/index.md` | Fetch/import tools, каталог, сохранение контента, машинный индекс, поиск фрагментов |
| Конспект | `src/notebook.mjs`: Markdown-файл, добавление callout-блоков | Чтение/поиск заметок, узлы и связи, backlinks, контролируемое обновление |
| Память | `.concept-loom/sessions/<sessionId>.json`, schemaVersion 2 | Профиль между курсами, полная история попыток, общий контекст курса, согласованная запись из нескольких процессов |
| OCR | Текстовая рекомендация применить OCR при плохом извлечении | Проверка качества по страницам, конвертеры, повторная обработка, provenance |
| Практика | choice/free-recall/prediction/debugging/transfer checkpoints | Сценарии, симуляции, выполнение кода, артефакты попыток, UI |

`src/bridge.mjs` объявляет только tools и возвращает текст/structuredContent. Он не объявляет MCP resources, UI resources или prompts. Сам сервер не вызывает LLM: модель, поиск в интернете и интерфейс вопросов предоставляет приложение. Именно эта граница определяет последствия перехода на LangChain.

Ответ на вопрос «сохраняем ли книгу и ее индекс»: **автоматической реализации нет**. Их может вручную подготовить пользователь или агент по руководству, но сервер не регистрирует оригинал, не проверяет хеш и не управляет индексом.

## 1. Организация промптов и полнота объяснений

Предлагается каталог `prompts/` с файлами `diagnose.md`, `research-course.md`, `plan-course.md`, `teach-lesson.md`, `practice.md`, `resume.md` и реестром `opf.yaml`. Общие учебные правила сохраняются как отдельная reference; адаптеры содержат только правила конкретного приложения.

OPF хранит метаданные, объявленные входы и упорядоченные сообщения в одном Markdown-файле. Для основы подходит `opf/0.2`; он не требует `version` в frontmatter. Используем простую подстановку строк и SHA-256 исходника. Реестр и загрузчик — отдельный слой от оркестрации. Проект экспериментальный, npm-пакет пока не опубликован; Python-пакет доступен. Следовательно, установка JavaScript-пакета с npm не должна стать предпосылкой первого этапа. Источники: [README OPF](https://github.com/stovo-team/open-prompt-format/blob/master/README.md), [синтаксис](https://github.com/stovo-team/open-prompt-format/blob/master/spec/SYNTAX.md), [schema 0.2](https://github.com/stovo-team/open-prompt-format/blob/master/spec/frontmatter-0.2.schema.json).

Вариант интеграции: OPF-файлы являются редактируемым источником правил; сборщик формирует статические reference для skills и проверяет их актуальность. В автономном режиме загрузчик возвращает сообщения API. В режиме приложения файл skill не становится настоящим system-message автоматически: адаптер читает инструкции в рамках полномочий своего приложения. Динамические входы курса передаются явно, а не через незаполненные шаблоны в установленном skill.

Предлагаемый контракт урока:

1. Цель: что учащийся сможет сделать после этого фрагмента.
2. Связь с уже известным и причина изучить новый шаг.
3. Объяснение механизма: предпосылки → шаги → вывод.
4. Разобранный пример с комментарием к каждому существенному переходу.
5. Ограничение, контрпример или типичная ошибка, если они существенны.
6. Схема или интерактивная модель, когда она помогает понять механизм.
7. Одно задание с ожидаемым действием учащегося.
8. Ссылка на конкретный раздел, страницу или фрагмент источника.

Полнота определяется этими составляющими и уровнем учащегося. Не устанавливаем универсальную норму числа слов. Уточняющий вопрос внутри урока получает полноценный ответ и затем возвращает к текущему шагу; он не создает новый курс. Краткие служебные ответы не обязаны повторять весь шаблон урока.

К каждому опубликованному уроку сохраняем идентификатор/хеш промпта и версию контракта данных, чтобы понимать, с какими инструкциями он был создан. Качество промптов оцениваем по примеру объяснения, фактическим ссылкам, реакции на пробел в знаниях и отсутствию преждевременного раскрытия решения. Платные модельные evals требуют отдельной настройки.

## 2. Визуализации и реальные возможности приложений

| Поверхность | Что подтверждено | Следствие для ConceptLoom |
|---|---|---|
| ChatGPT MCP Apps | HTML UI в iframe; стандартная связь с MCP tools | Можно построить единый виджет курса, карты и задания |
| ChatGPT desktop | При доступной функции HTML preview `.html`/`.htm` могут открываться интерактивно | Локальный HTML — переносимый способ просмотра; доступность проверяется |
| Codex в этом окружении | Доступны browser panel, skill `visualize`, создание отдельных чатов и automations | Использовать возможности адаптера, проверять их наличие при запуске |
| Claude Desktop с MCP Apps | Стандарт поддерживает объявление HTML UI и обмен с сервером | Переиспользовать виджеты там, где приложение объявляет поддержку |
| Claude Code Desktop | Artifacts создают интерактивные страницы при доступной функции и авторизации | Дополнительный способ показать учебный материал; требуется учитывать CSP |
| CLI и прочие приложения | UI может отсутствовать | Markdown/Mermaid/text и задания в чате остаются доступными |

Документация OpenAI описывает MCP Apps UI в ChatGPT. HTML preview зависит от поверхности и доступности функции. Состояние виджета относится к отдельному UI и не заменяет долговременное хранилище курса. Источники: [MCP и UI quickstart](https://developers.openai.com/plugins/build/app-quickstart), [HTML preview](https://learn.chatgpt.com/docs/artifacts-viewer?surface=app), [хранение состояния UI](https://developers.openai.com/plugins/build/chatgpt-ui).

MCP Apps предоставляет UI resources, capability negotiation и обмен между iframe, приложением и сервером. Для неподдерживаемых клиентов предусмотрен текстовый результат. Это основание для общего UI; конкретную поддержку Claude Code Desktop нельзя выводить только из поддержки Claude Desktop. Источник: [MCP Apps overview](https://apps.extensions.modelcontextprotocol.io/api/documents/overview.html).

Claude Code Artifacts — отдельная возможность: одна страница, ограничения CSP и подключений, публикация в аккаунт Claude. Нельзя считать локальный Markdown-блок автоматической интерактивной страницей. При недоступной функции используем локальный HTML/браузер. Источник: [Claude Code Artifacts](https://code.claude.com/docs/en/artifacts).

Предлагается semantic diagram API: узлы `{id, label, kind, mastery}` и связи `{from, to, relation}`. Из этих данных строим несколько представлений. Стили передаются профилем приложения: светлая/темная тема, крупные читаемые подписи, сдержанные акценты, понятные категории. По умолчанию не более 8–12 видимых узлов; подробности раскрываются отдельно.

Mermaid: согласованное направление зависимостей, подграфы по смыслу, classDef для типов/статусов, короткие подписи ребер, пояснение вне схемы. Проверяем наличие узлов, уникальность IDs и направления ребер. Произвольный Mermaid — дополнительный advanced input. Если приложение игнорирует тему, смысл должен сохраняться в подписях.

HTML/SVG: полезны для раскрытия узлов, изменения параметров, пошагового выполнения и наблюдения результата. Граф знаний и учебный roadmap используют общую модель данных, но показываются отдельно: в первом есть смысловые отношения, во втором — порядок и предпосылки уроков.

## 3. Большие темы, курс и уроки по расписанию

Путь учащегося:

1. Уточнить цель, опыт, необходимые предпосылки, язык, время на урок и желаемую длительность курса. Для «хочу изучить LangChain» выяснить, какую систему человек хочет построить и знает ли Python/API.
2. Провести короткую диагностику: самооценка и несколько содержательных задач. Не приравнивать опыт в резюме к доказанному пониманию.
3. Обязательно искать материалы и открывать подходящие документы/программы курсов. Сохранять результаты исследования, включая неудачные запросы и ограничения доступа.
4. Сопоставить материалы с целью: основные, для предпосылок, дополнительные; явно указать старые версии и расхождения.
5. Составить краткий roadmap. Каждый урок содержит цель, темы, зависимости, примерную длительность, материалы и практику.
6. Показать roadmap; после согласия зафиксировать его версию. Отдельно предложить дни, время и часовой пояс расписания.
7. После согласия на расписание создать standalone scheduled task в выбранном приложении. Новые запуски восстанавливают курс из общего хранилища.
8. Открыть урок с объяснением и практикой; ждать ответа и продолжать тот же урок при последующих вопросах.

Поиск должен рассматривать документацию, книги, статьи и программы курсов. Это категории поиска, а не требование придумать книгу или курс, если подходящих доступных материалов нет. В roadmap нельзя помечать прочитанным источник, доступный только по поисковому сниппету. При недоступном интернете сохраняем черновик и ограничения; статус «исследовано» требует фактического открытия достаточных источников.

Программы других курсов дают сведения о покрытии тем и предпосылках. Их порядок адаптируется к цели учащегося. Например, публичная программа [LangChain Academy](https://academy.langchain.com/courses/foundation-introduction-to-langchain-python) содержит блоки об агентах и инструментах; [MIT OCW syllabus](https://ocw.mit.edu/courses/6-0001-introduction-to-computer-science-and-programming-in-python-fall-2016/pages/syllabus/) показывает требования и учебные цели. Это примеры доступных программ, не готовый персональный roadmap.

Для Stepik изучен официальный API с иерархией курса и правилами авторизации. Доступ к материалам от имени аккаунта требует соответствующей авторизации. [Stepik API](https://help.stepik.org/article/64188). Для Udemy начальный вариант — открытая страница курса и видимая программа; доступность универсального публичного API для требуемого контента не подтверждена. Полные закрытые уроки регистрируем только при доступе через разрешенный инструмент или предоставленные файлы.

### Поведение расписания

Оба приложения подтверждают отдельные чаты/сессии для scheduled runs. ChatGPT использует standalone scheduled tasks; задачи внутри существующего чата возвращаются в него. Claude Code Desktop запускает свежую сессию; локальным задачам нужны открытое приложение и работающий компьютер. Источники: [ChatGPT scheduling](https://learn.chatgpt.com/docs/automations), [Claude Code Desktop scheduling](https://code.claude.com/docs/en/desktop-scheduled-tasks).

Предлагается один активный scheduler на курс, с выбранным приложением. Обе интеграции доступны, но два таймера не должны независимо выпускать один урок. Перенос в другое приложение обновляет scheduler binding при сохранении courseId и истории.

Промпт запуска содержит абсолютный learningWorkspace, courseId, версию контракта, выбранный skill и правила:

- Загрузить курс, профиль, предыдущий результат и просроченные повторения.
- Атомарно получить следующий допустимый урок и runId.
- Если есть незавершенный урок, по умолчанию показать продолжение/ссылку и короткое повторение; не объявлять его освоенным из-за наступления даты. Режим выпуска следующих уроков независимо от прохождения — отдельная согласованная настройка.
- Прочитать релевантные источники; собрать материал для конкретного уровня учащегося.
- Сохранить урок и context capsule; записать связанный chat/session ID, если приложение его предоставляет.
- Подготовить объяснение и первое задание. Автономный запуск останавливается в `awaiting-learner`, не имитирует ответ учащегося.
- При вопросе пользователя загрузить тот же lessonId, ответить с опорой на материалы и продолжить урок.

Расписание хранит IANA timezone, согласованную локальную дату/время, cadence, missed-run policy и receipt приложения. Время из окружения не подменяет выбранный пояс. Для текущей беседы клиент сообщает `Asia/Bishkek`; для будущего курса пояс спрашиваем у учащегося.

Пропуск запуска не означает пропуск урока. Используем idempotency key `(courseId, lessonId, roadmapRevision)` и lease с истечением срока. Завершенный курс приостанавливает задачу через доступную интеграцию; если автоматическая пауза недоступна, готовится действие для пользователя.

Учебное хранилище имеет стабильный корень. Worktrees и cloud clones не должны случайно создавать отдельные пустые памяти. Для локального варианта — один явно настроенный learningWorkspace; для облака — доступное удаленное хранилище с теми же контрактами.

## 4. Источники: сохранение и индексация

Предлагаемая структура учебного workspace:

```text
learning-workspace/
  .concept-loom/
    profile.json
    courses/<courseId>/course.json
    sessions/<sessionId>.json
    events/<courseId>.jsonl
    sources/catalog.json
    sources/<sourceId>/manifest.json
    sources/<sourceId>/original/<file>
    sources/<sourceId>/prepared/document.md
    sources/<sourceId>/prepared/structure.json
    sources/<sourceId>/prepared/chunks.jsonl
    sources/<sourceId>/prepared/index.md
    indexes/notes.json
    runs/<runId>.json
  vault/
    Courses/<courseId>/Roadmap.md
    Lessons/<lessonId>.md
    Concepts/<conceptId>.md
    Sources/<sourceId>.md
    Personal/
  exercises/<exerciseId>/
```

Оригинал сохраняется неизменным, если импортируется файл/книга или разрешено полное сохранение веб-материала. Для больших локальных файлов можно согласовать ссылку на исходник; manifest различает `copied` и `referenced`. Хеш обнаруживает замену. Если инструмент вернул только извлеченный текст/summary, manifest отмечает это и не утверждает наличие оригинальной страницы. Если разрешены только метаданные, сохраняем только их.

Manifest источника: стабильный sourceId, canonical URL либо original path, title/author, тип, язык, издание/версия, publicationDate, accessedAt, contentHash, формат полученного содержимого, coverage, access status, extraction tool/version/options и ссылки на prepared artifacts. Состояния: `discovered`, `metadata-only`, `fetched`, `prepared`, `indexed`, `blocked`, `failed`. Ошибка/ограничение сопровождается причиной и возможным следующим действием.

Chunk: sourceId, версия содержимого, chunkId, headingPath, текст и locator. Для PDF locator содержит physicalPage, printedPageLabel при наличии и bbox; для EPUB — spine/section; для видео — timestamps; для кода — путь/commit/lines. Вектор или краткое описание не заменяет этот фрагмент.

Сначала навигация по оглавлению и поисковый индекс текста. Chunking сохраняет смысловые разделы, порядок книги и целостность таблиц. Размер ограничивается токенами, без склеивания несвязанных глав. Поиск возвращает выдержку, locator, исходный файл/URL и качество извлечения. Сравниваем кандидатов через контекст вопроса, затем читаем фрагмент целиком.

На первом этапе достаточно файлового каталога и lexical search. Семантический индекс подключается за тем же search contract, если на реальной библиотеке улучшает retrieval. Embeddings считаются производными: хранят модель, параметры и версию контента; пересоздаются при изменении источника. Пользовательские notes и fetched sources индексируются отдельно, чтобы отличать личное утверждение от внешнего доказательства.

Fetch выполняется через доступные инструменты приложения; для воспроизводимой подготовки нужен инструмент, возвращающий контент и метаданные. Собственный downloader — отдельный адаптер с ограничениями размера/времени, проверкой типа и redirect policy. Подготовка книги не должна блокировать чат на весь файл: сохраняются прогресс и очередной раздел.

## 5. Obsidian-совместимый граф знаний

Одна заметка — одно устойчивое понятие или другой учебный объект. Узлы: concept, source, lesson, exercise. Для понятия сохраняем стабильный ID, aliases и свойства. Связи имеют смысл: `requires`, `explains`, `example-of`, `contrasts-with`, `supported-by`, `applied-in`. У prerequisite DAG не может быть циклов, у общего смыслового графа циклы допустимы.

Markdown заметок использует `[[wikilinks]]` или обычные Markdown links. Их поддержка подтверждена [Obsidian Internal links](https://help.obsidian.md/Linking+notes+and+files/Internal+links). Представление связей в YAML и служебных блоках — наш контракт; индекс строится из файлов, а не становится единственным экземпляром знаний.

Агент умеет читать заметку, находить понятие/alias, проходить соседние узлы и предпосылки, искать backlinks и связанные источники. Контекст ограничивается текущим уроком и ближайшими релевантными связями. Большой граф не помещается целиком в prompt.

Редактирование:

- Пользователь может писать Markdown любым редактором и открывать папку как vault в Obsidian.
- Свои объяснения агент пишет в `<!-- concept-loom:begin -->` / `<!-- concept-loom:end -->` с указанием происхождения.
- Перед записью сравнивается хеш файла. Изменение пользователем или другим чатом вызывает перечитывание/слияние, не молчаливое замещение.
- За пределами служебного блока агент добавляет предложение/комментарий; редактирование пользовательского текста требует явного поручения.
- Изменение исходного файла инвалидирует его индекс. Обнаруживаются dangling links, неоднозначные aliases и перемещения файлов.
- История обновлений и резервная копия позволяют восстановить предыдущее содержание.

Статус освоения вычисляется из evidence; наличие конспекта или прочтение книги не доказывает mastery. Пользовательское утверждение, вывод агента и проверенное утверждение источника различаются по provenance.

## 6. Python, LangChain и LangGraph

| Подход | Польза | Стоимость/ограничение | Вывод |
|---|---|---|---|
| Расширить существующий Node MCP | Сохраняет простую установку и использование модели приложения | Сложные конвертеры удобнее подключать отдельно | Подходит для общих данных и host adapters |
| Node MCP + Python document pipeline | Хорошо подходит Docling/OCR; не требует второго LLM-loop | Дополнительный Python runtime для подготовки документов | Рекомендуемый первый путь |
| Полный Python/LangGraph agent + MCP | Своя state machine, interrupts и долговременное выполнение вне приложения | Настройка модели/авторизации, среда выполнения, UI и scheduler integration остаются отдельной работой | Рассмотреть как дополнительный автономный режим |

LangGraph предлагает сохраняемое состояние workflow и управление сложным выполнением; LangChain предоставляет инструменты и интеграции, в том числе MCP. Это возможности для собственного агентного runtime. Они сами по себе не предоставляют новое окно чата в чужом приложении, индекс книги или политику знаний. Источники: [LangGraph overview](https://docs.langchain.com/oss/python/langgraph/overview), [persistence](https://docs.langchain.com/oss/python/langgraph/persistence), [LangChain MCP](https://docs.langchain.com/oss/python/langchain/mcp).

Предлагается сохранить публичные MCP contracts, добавить Python подготовку документов и отдельный optional runtime позднее. Если пользователь предпочтет полный переход сейчас, сначала переносим детерминированные инструменты и compatibility fixtures, затем подключаем agent loop. Профиль, источники, курс и vault не должны зависеть от языка реализации.

Решение о полном переходе принимаем по необходимости автономного исполнения и результатам retrieval/OCR, а не по популярности библиотеки. LangGraph graph описывает выполнение программы; граф знаний описывает предметные связи. Это разные структуры.

## 7. Память и надежность состояния

Сейчас сохраняются цель, topic, phase/mode, route, secured/gaps, evidence, extensions, currentStep/nextStep, learnerContext и последний checkpoint. Evidence содержит счетчики, dimensions, confidence/calibration, последнюю попытку и reviewAfter. Интервалы повторения — простая последовательность 1/3/7/14/30 дней. Полного журнала попыток, отдельного профиля и общего состояния курса нет.

Найденные ограничения по чтению кода:

1. `saveLearningState` в `src/progress.mjs:77` заменяет отсутствующие `route`, `secured`, `gaps` пустыми массивами. Внешний вызов с частичным snapshot может стереть их. Skill требует передавать полное состояние, но контракт не предотвращает ошибку.
2. `rename` обеспечивает замену одного файла, но не согласованное read-modify-write. Параллельные процессы могут потерять результат друг друга. Временный файл использует PID; параллельные вызовы внутри одного процесса используют один путь.
3. `assessCheckpoint` в `src/checkpoints.mjs:106` удаляет token до окончательной проверки аргументов и до записи состояния. `src/bridge.mjs:169` выполняет grading, а потом persistence. При ошибке состояние не сохранено, token уже расходован. Формулировка «atomically persist» в описании tool превышает фактическую гарантию.
4. Карточки живут в Map одного процесса, 6 часов. Ответы из другого чата/процесса и восстановление после перезапуска не поддерживаются. Это намеренная эпhemerality, но для интерактивной практики потребуется другой lifecycle.
5. Есть `revision`, но нет проверки ожидаемой revision. Evidence хранит агрегаты и последнюю попытку; потеряно различие немедленной проверки и успешного отложенного воспроизведения. Успешная попытка с подсказкой также увеличивает счетчик успехов.
6. `addNotebookEntry` добавляет запись по пути без проверки, что файл ранее создан через `beginNotebook`; сервер пока не умеет читать этот конспект. Ограничение пути проверяет строковое расположение, не разрешенный реальный путь через symlink/junction.

Предлагаемые слои памяти: learner profile; состояние курса и урока; журнал попыток; vault понятий; каталог источников; небольшой context capsule для нового чата. Временная карточка проверки остается отдельным объектом с приватными критериями.

Изменения надежности: patch/snapshot semantics задаются явно; validate-before-mutate; unique temporary paths; блокировка на запись из нескольких локальных процессов; expectedRevision; idempotent attemptId; журнал событий и recovery; фиксация результата до расходования карточки. Версии 1/2 читаются и мигрируют с резервной копией.

Для первых локальных изменений файловая модель допустима с этими гарантиями. При транзакции сразу над несколькими объектами и постоянной конкуренции подходит SQLite за storage interface; выбор драйвера и поддерживаемой Node/Python версии включается в спецификацию. Простое `rename` нельзя называть транзакцией курса.

Интервал повторений должен учитывать отложенное воспроизведение, hints и тип задания. Сначала исправляем модель evidence и журналируем данные; переход к более сложному алгоритму требует отдельных критериев качества. Оценка открытого ответа моделью хранит rubric/version и основание решения, чтобы учащийся мог оспорить ошибку.

## 8. OCR и извлечение документов

Предлагается page-level pipeline: определить текстовый слой и качество → извлечь структуру → применить OCR только к нужным страницам → проверить таблицы/формулы/отрицания → подготовить chunks с provenance.

Docling поддерживает разные OCR backends и структурированную подготовку документа; OCRmyPDF полезен для добавления/замены текстового слоя. Сначала пилот на русско-английских документах, таблицах, двух колонках и формулах; окончательный default выбираем по измерениям. Источники: [Docling OCR](https://docling-project.github.io/docling/_generated/examples/full_page_ocr/), [chunking](https://docling-project.github.io/docling/concepts/chunking/), [OCRmyPDF modes](https://ocrmypdf.readthedocs.io/en/latest/advanced.html), [cookbook](https://ocrmypdf.readthedocs.io/en/latest/cookbook.html).

Оригинал сохраняется. На странице фиксируются engine/version/languages, качество и проблемы. Confidence может отсутствовать; не придумываем значение. Текстовый PDF иногда содержит некачественный слой, поэтому наличие символов не равно качественному извлечению. Mixed PDF обрабатывается по страницам; OCR sidecar не принимается за полный текст документа, если часть страниц пропущена.

Для важных формул/таблиц сохраняется ссылка на исходный crop/page; проверка зрением или уточнение учащемуся обязательно при неоднозначности. Vision fallback — выборочная обработка сложной страницы после проверки доступного инструмента и условий отправки документа. Нельзя молча заменить сомнительное распознавание убедительной формулировкой.

Конвертер работает отдельным процессом с таймаутом, лимитом памяти/страниц, checkpoints задания и повторяемыми настройками. Вариант для Windows выбирается отдельно: Python libraries либо доступная контейнерная/WSL среда. Не предполагаем macOS `textutil` или bash-команды из нынешнего руководства на Windows.

## 9. Интерактивная практика

Три категории заданий:

- Сценарий решений: последовательность действий, состояние ситуации, наблюдаемые последствия. Например, выбрать стратегию извлечения документов и объяснить изменение результата.
- Управляемая модель: sliders/step controls, предсказание до запуска, сравнение с результатом. Например, изменить chunk size и посмотреть покрытие заданных цитат на подготовленном наборе.
- Coding lab: starter files, сформулированная цель, проверки результата, подсказки по запросу, разбор попытки и перенос на другой случай.

У каждого exercise есть exerciseId, lessonId, формат, objectives/conceptIds, публичная постановка, приватная rubric/solution, начальные файлы и версия. Attempt хранит точный ответ или artifactHash, результат checks, подсказки, confidence, feedback и mastery evidence.

HTML UI не считается изолированной средой для Python/shell. Для JavaScript симуляции подходит browser sandbox; Python/Node задания запускаются в отдельной ограниченной среде с лимитами времени/ресурсов. Исполнение произвольного пользовательского кода через обычный MCP grading tool недопустимо: нужен отдельный execution contract.

Оценивание отправляет попытку на сервер или передает ее в чат через разрешенный host bridge. Правильный ответ не помещается заранее в HTML/JS assessed exercise. В автономном offline quiz с client-side ответами нельзя обещать concealment; такие упражнения отмечаются как self-check и не дают подтвержденную mastery без дополнительной проверки.

Если UI не связан с сервером, доступен экспорт attempt JSON/текста для отправки в чат. localStorage/widget state сохраняют положение интерфейса; прогресс курса фиксируется сервером после проверки попытки. Модельные оценки открытых решений остаются отличимы от проверок исполняемого результата.

## Предлагаемый порядок реализации

1. **Учебные ответы и надежность:** OPF sources/build, структура объяснений, сохранение состояния без потерь, совместимость schema v1/v2, semantic Mermaid. Это сразу улучшает нынешний урок.
2. **Библиотека материалов и vault:** manifests, import/prepared text, locators/chunks, поиск и неизменные оригиналы; concept notes, связи и безопасное обновление. Здесь подключается Python document pipeline.
3. **Курс и две интеграции расписания:** shared course/lesson schemas, research receipts, roadmap approval, context capsule, idempotent dispatch, pause/catch-up, Codex и Claude adapters. Сначала ручной dispatch, затем native scheduler.
4. **Практика и графический интерфейс:** общие HTML views для карты/сценария, интеграция с MCP Apps и доступными host surfaces, coding execution adapter.
5. **Дополнительный автономный runtime:** только при выбранной необходимости; Python/LangGraph использует уже определенные данные и MCP contracts.

Это порядок зависимостей, а не оценка длительности. Работа по обоим приложениям использует один contract suite; ручная проверка UI/scheduler нужна в каждом приложении, потому что тест MCP-сервера не подтверждает открытие реального нового чата.

## Что должно доказывать реализацию

- Урок раскрывает механизм и пример; источник ведет к прочитанному фрагменту; вопрос учащегося не теряет текущий шаг.
- OPF проверяется официальным reader либо документированным совместимым загрузчиком; generated skills не расходятся с источниками.
- Книга импортируется с оригиналом/хешем; поиск возвращает правильную страницу; новая редакция инвалидирует chunks; metadata-only источник не считается прочитанным.
- Заметка пользователя меняется вручную: индекс обновляется, текст сохраняется, связи доступны агенту.
- Два процесса одновременно сохраняют ответы: результат не теряется. Невалидный ответ/ошибка диска не уничтожает возможность завершить оценивание.
- После согласования курс запускается в новом чате каждого приложения; без согласия scheduler остается неактивным. Повтор запуска не выпускает дубль урока.
- Урок в scheduled chat остается пригодным для вопросов; следующий запуск корректно учитывает незавершенную практику.
- OCR проверяется на документах с известным эталоном и сохраняет координаты; неразборчивый фрагмент отмечен, а не сочинен.
- HTML попытка сохраняется в долговременную память; ответы отсутствуют в исходнике assessed exercise; coding execution соблюдает лимиты.

В этом исследовательском этапе выполнены чтение кода и проверка первичной документации. Тесты, установка зависимостей, запуск OCR на книгах и live scheduled tasks не выполнялись. Документ не утверждает, что какая-либо из новых функций уже работает.
